## 1. 部署架构总览

```
用户请求
    │
    ▼
Cloudflare CDN（全球边缘）
    │
    ├── 静态页面/资源 ──► Cloudflare Pages 直接响应（长期缓存）
    │
    └── API 请求 ──► Cloudflare Workers (Hono)
                            │
                  ┌─────────┼─────────┐
                  ▼         ▼         ▼
                D1        KV       public/images
            (SQLite 数据库) (可选缓存) (Pages CDN 分发)
```

### 1.1 组件清单

| 组件     | 技术                     | 部署位置                  | 说明                               |
| -------- | ------------------------ | ------------------------- | ---------------------------------- |
| 前端     | Astro 5 (SSG)            | Cloudflare Pages          | 静态预渲染，构建时从 API 获取数据  |
| API      | **Hono on Workers**      | Cloudflare Workers        | `apps/api/`，独立部署，RESTful API |
| 数据库   | Cloudflare D1            | Cloudflare 边缘           | SQLite 兼容，全球分布式读          |
| 图片存储 | `public/images/`         | Cloudflare Pages 静态资源 | 图片随仓库管理，Pages CDN 分发     |
| CDN      | Cloudflare               | 全球边缘                  | 静态资源加速、DDoS 防护            |
| DNS      | Cloudflare DNS           | Cloudflare                | 代理模式（橙色云），WAF 自动启用   |
| 邮件     | Cloudflare Email Workers | Cloudflare                | 评论通知、系统告警（可选）         |
| 监控     | Cloudflare Analytics     | Cloudflare                | 性能指标 + Workers 日志            |

## 2. 环境划分

| 环境       | 用途               | 数据库             | 域名示例                    |
| ---------- | ------------------ | ------------------ | --------------------------- |
| local      | 本地开发           | D1 本地 (wrangler) | API :8788 + Web :4322       |
| preview    | PR 预览 / 功能验证 | D1 preview 实例    | `<branch>.pages.dev`        |
| production | 线上正式环境       | D1 生产实例        | `example.com` + API Workers |

### 2.1 环境变量管理

本地开发只使用根目录统一 `.env`：

| 模板 | 生成的本地文件 | 内容 | 本地是否必须 |
| ---- | -------------- | ---- | ------------ |
| `.env.example` | `.env` | 本地初始密码 + 两个 JWT 密钥 + 两个 Web URL | 必须 |

推荐直接在 VS Code、Cursor 等编辑器的文件树中复制模板并重命名，不要求使用 `cp` 或 `echo` 命令。

Wrangler 使用 `--env-file ../../.env`，Astro 使用 Vite `envDir`，二者读取同一文件。只有 `PUBLIC_` 前缀变量会进入浏览器代码；`ADMIN_INITIAL_PASSWORD`、`JWT_SECRET` 和 `JWT_REFRESH_SECRET` 不会被 Astro 暴露。

生产环境仍建议分别在 Workers 和 Pages Dashboard 中配置对应变量，不上传或提交本地 `.env`。

Pages 与 Workers 使用各自的 `*.pages.dev`、`*.workers.dev` 默认域名时属于跨站请求。管理后台会在当前标签页保存短期会话令牌并自动轮换，因此不依赖第三方 Cookie；如果改用同一主域名下的两个子域名，HttpOnly Cookie 仍会作为兼容通道使用。

- 生产 Secrets 通过 `wrangler secret put` 或 Dashboard 设置
- `JWT_SECRET` 与 `JWT_REFRESH_SECRET` 必须使用不同的高熵随机值
- `ADMIN_INITIAL_PASSWORD` 仅用于空数据库首次登录，生产必须自定义，成功改密后删除
- 禁止在代码中硬编码任何密钥
- 即使秘密从 Git 删除，也视为已泄露并立即轮换

## 3. 本地开发环境搭建

### 3.1 前置依赖

| 工具                | 版本   | 用途                |
| ------------------- | ------ | ------------------- |
| Node.js             | 22 LTS | 运行时              |
| pnpm                | 9+     | 包管理器            |
| Cloudflare Wrangler | 最新   | 本地开发 + 部署 CLI |

### 3.2 首次启动流程

```bash
# 1. 克隆仓库
git clone https://github.com/elite-silab/nami-blog.git && cd nami-blog

# 2. 安装依赖
pnpm install
```

在编辑器中完成以下操作：

1. 复制根目录 `.env.example`。
2. 将副本命名为根目录 `.env`。
3. 本地使用默认端口时，模板内容可以直接使用。
4. 生产环境必须在 Cloudflare Dashboard 设置两个 JWT Secret 和一次性管理员密码，不能复用模板值。

然后执行：

```bash
# 3. 启动开发环境（自动执行本地 D1 迁移，API + 前端并行）
pnpm run dev
# → API:  http://localhost:8788 (Workers + D1 binding)
# → 前端: http://localhost:4322 (Astro SSG dev server)
```

> 完整图形化操作和常见问题请参阅 [小白上手指南](小白上手指南.md)。

### 3.3 创建管理员账号

本地空数据库首次登录时，API 会创建模板管理员：

- 用户名固定为 `admin`
- 密码来自根目录 `.env` 的 `ADMIN_INITIAL_PASSWORD`
- 本地模板密码只允许 `localhost` 或 `127.0.0.1` 请求触发
- bcrypt cost 12 存储；已有管理员时不会创建或重置

生产空数据库也支持 Dashboard 一次性初始化：将 `ADMIN_INITIAL_PASSWORD` 设置为 Workers Secret，使用至少 12 个字符的自定义值，并通过 HTTPS 登录。生产环境明确拒绝 `nami-local-admin`。首次登录后应在后台安全设置中修改密码并删除该 Secret。

生产迁移不会创建固定默认管理员。维护者也可以不设置一次性 Secret，改用受控交互脚本初始化远程 D1：

```bash
pnpm run db:seed -- --remote
```

远程模式会要求输入 `CREATE` 二次确认。管理员密码不得写入仓库、文档、Shell 历史或聊天记录。

本地维护者如需交互式创建或更新账号，也可运行 `pnpm run db:seed`；这不是新手首次启动的必需步骤。

## 4. CI/CD 流水线

### 4.1 工具选择

| 工具               | 用途                       |
| ------------------ | -------------------------- |
| GitHub Actions     | Lint、类型检查、测试和构建 |
| Cloudflare Pages   | 前端自动构建 + 部署（SSG） |
| Cloudflare Workers | Git 集成自动迁移并部署 API |

### 4.2 CI 流水线（每次 PR / Push 到 main）

```yaml
# .github/workflows/ci.yml（示意）
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }

      - run: pnpm install --frozen-lockfile
      - run: pnpm run check # typecheck + lint
      - run: pnpm run test # Vitest
      - run: pnpm run build # API + Astro 生产构建

  # ── D1 迁移验证 ──
  migration:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm wrangler d1 migrations apply nami-blog --local --config apps/api/wrangler.toml
```

### 4.3 CD 部署流程

```
Push to main
    │
    ├─► GitHub Actions CI
    │     → lint / typecheck / test / build
    │
    ├─► Cloudflare Workers Git 集成
    │     → D1 migration → Worker deploy
    │
    └─► Cloudflare Pages Git 集成
          → Astro build → Pages deploy
```

GitHub Actions 当前只做质量检查，不保存 Cloudflare Token，也不负责发布。生产分支应启用 GitHub branch protection，要求 CI 通过后才能合并；合并到 `main` 后由两个 Cloudflare Git 集成部署。

## 5. Cloudflare 配置

### 5.1 Workers API 项目设置 (`apps/api`)

| 配置项   | 值                                   |
| -------- | ------------------------------------ |
| 运行时   | Cloudflare Workers（Hono 框架）      |
| 构建命令 | `pnpm --filter @nami/api build`       |
| 部署命令 | `pnpm --filter @nami/api deploy:full` |
| 入口文件 | `src/index.ts`                       |
| D1 绑定  | `DB` → `nami-blog`                   |

### 5.2 Pages 前端项目设置 (`apps/web`)

| 配置项    | 值                                     |
| --------- | -------------------------------------- |
| 框架      | Astro 5（`output: "static"` SSG 模式） |
| 构建命令  | `pnpm run build:web`                   |
| 输出目录  | `apps/web/dist`                        |
| Node 版本 | 22                                     |
| 环境变量  | `PUBLIC_API_URL` 指向 Workers API 地址 |
| 自动部署  | 连接 GitHub，`main` → 生产，PR → 预览  |

### 5.3 DNS 与代理

| 记录  | 类型            | 代理状态          | 说明         |
| ----- | --------------- | ----------------- | ------------ |
| `@`   | CNAME → Pages   | Proxied（橙色云） | 前端静态站点 |
| `api` | CNAME → Workers | Proxied（橙色云） | Workers API  |

### 5.4 缓存规则（Cache Rules）

```
# 静态资源：长期缓存（文件名含 hash）
(uri.path ~ "\\.(js|css|png|jpg|jpeg|gif|webp|avif|svg|woff2)$")
  → Cache TTL: 1 year, Browser TTL: 1 year

# HTML 页面：短时缓存
(uri.path ~ "/$") or (uri.path ~ "/blog/")
  → Cache TTL: 60s, Browser TTL: 60s

# API 响应：不缓存
(uri.path ~ "^/api/")
  → Bypass Cache

# 管理后台：不缓存
(uri.path ~ "^/admin")
  → Bypass Cache
```

Workers 的公开 GET 接口会返回短时 `Cache-Control`（60 秒浏览器缓存、300 秒边缘建议缓存）。如果需要让 Cloudflare Cache Rules 接管缓存，可针对公开读接口单独放行；登录、评论提交、后台接口和健康检查必须保持 bypass/no-store。

Pages 项目使用 `apps/web/public/_headers` 下发 `nosniff`、`frame-ancestors`、Referrer-Policy、Permissions-Policy 和 CSP；Workers API 也会返回对应的基础安全头。

### 5.5 WAF 与安全

- **Bot Management**：启用，拦截已知恶意 Bot
- **Rate Limiting Rules（需在 Cloudflare Dashboard 配置）**：
  - `/api/v1/auth/*`：每 IP 10 次/分钟
  - `/api/v1/comments`：每 IP 5 次/分钟
  - 全局：每 IP 100 次/分钟
- **Managed Rules**：启用 OWASP Core Ruleset
- **SSL/TLS**：Full (Strict) 模式，强制 HTTPS
- **HSTS**：启用，max-age 1 年，包含子域名

## 6. 数据库运维

### 6.1 备份策略

| 类型        | 频率           | 保留期 | 方式                                  |
| ----------- | -------------- | ------ | ------------------------------------- |
| Time Travel | 自动持续       | 30 天  | D1 内置，可回溯任意时间点             |
| 定期导出    | 每日 02:00 UTC | 30 天  | `wrangler d1 export` → 本地归档 / Git |
| 手动快照    | 重大变更前     | 永久   | `wrangler d1 export` → 本地归档       |

### 6.2 迁移执行

```bash
# 本地
pnpm run db:migrate

# 远程 preview
pnpm run db:migrate:preview

# 远程生产（谨慎）
pnpm run db:migrate:prod
```

生产迁移前检查清单：

- [ ] D1 Time Travel 可用（自动保留 30 天）
- [ ] 迁移在 preview 环境验证通过
- [ ] 无破坏性变更（D1 不支持 `DROP COLUMN`，需重建表）
- [ ] 大表操作评估性能影响

### 6.3 D1 监控

| 指标         | 告警阈值         | 方式                 |
| ------------ | ---------------- | -------------------- |
| 读取单位用量 | 接近免费额度上限 | Cloudflare Dashboard |
| 写入单位用量 | 接近免费额度上限 | Cloudflare Dashboard |
| 存储大小     | > 500MB          | Dashboard            |
| 查询错误率   | > 1%             | Workers Analytics    |

## 7. 监控与告警

### 7.1 监控栈

| 层级         | 工具                                 | 覆盖范围                   |
| ------------ | ------------------------------------ | -------------------------- |
| 前端性能     | Cloudflare Web Analytics             | LCP、FID、CLS、TTFB        |
| 前端错误     | Sentry (Browser SDK)                 | JS 异常、资源加载失败      |
| Workers 性能 | Cloudflare Workers Analytics         | 响应时间、错误率、CPU 时间 |
| Workers 日志 | Cloudflare Logpush / `wrangler tail` | 实时日志                   |
| 可用性       | UptimeRobot / Better Stack           | 外部探测                   |

### 7.2 告警规则

| 场景            | 阈值               | 通知渠道 |
| --------------- | ------------------ | -------- |
| 站点不可用      | 连续 2 次探测失败  | 邮件     |
| Workers 错误率  | > 5%（5 分钟窗口） | 邮件     |
| D1 用量接近上限 | > 80% 免费额度     | 邮件     |
| SSL 证书过期    | < 14 天            | 邮件     |

### 7.3 健康检查端点

```
GET /api/v1/healthz
# 兼容探针：GET /healthz
```

响应：

```json
{
  "status": "ok",
  "service": "nami-blog-api"
}
```

当前健康检查只验证 Worker 进程可响应，不主动执行 D1 探测；D1 深度探测应单独配置受保护的监控任务，避免对公开端点增加数据库负载。

## 8. 日志规范

### 8.1 日志格式

Pages 与 Workers API 使用 `console.log` 输出结构化日志：

```json
{
  "level": "info",
  "ts": "2026-07-25T10:30:00Z",
  "caller": "apps/api/src/routes/posts.ts",
  "msg": "posts listed",
  "count": 20,
  "duration_ms": 12
}
```

实时查看 API 日志：`wrangler tail --config apps/api/wrangler.toml`

### 8.2 日志安全

**禁止记录**：

- Authorization / Cookie 头
- 密码、Token、一次性验证码
- 用户邮箱明文（脱敏 `u***@example.com`）
- JWT Secret

## 9. 发布与回滚

### 9.1 发布流程

```
1. feature 分支提交 Pull Request
2. GitHub Actions CI 全部通过
3. 人工验证 Pages preview（如已启用）
4. squash merge 到受保护的 main
5. Cloudflare Workers 和 Pages Git 集成自动部署
6. 检查 `/api/v1/healthz` 与前台页面
7. 打 Git Tag：v1.x.x
```

### 9.2 回滚策略

| 组件          | 回滚方式                               | 耗时     |
| ------------- | -------------------------------------- | -------- |
| Pages (前端)  | Dashboard 回滚到上一部署               | < 30s    |
| Workers (API) | `wrangler rollback` 或重新部署上一版本 | < 30s    |
| D1 数据库     | Time Travel 回溯或兼容迁移             | 视数据量 |

**回滚原则**：

- Pages 回滚一键完成，不执行高风险 schema 变更
- 回滚后在 `main` 上修复，走正常发布流程
- 回滚事件记录到审计日志

## 10. 灾难恢复

### 10.1 场景与预案

| 场景             | RTO       | RPO      | 恢复步骤                         |
| ---------------- | --------- | -------- | -------------------------------- |
| Pages 部署异常   | < 1 分钟  | 0        | Dashboard 回滚上一部署           |
| Workers 部署异常 | < 1 分钟  | 0        | `wrangler rollback` 回滚上一版本 |
| D1 数据损坏      | < 5 分钟  | < 1 小时 | Time Travel 回溯到正常时间点     |
| D1 数据丢失      | < 30 分钟 | < 1 天   | 从本地备份导入                   |
| Cloudflare 故障  | 依赖 CF   | 依赖 CF  | 切换 DNS 到备用 CDN（极端预案）  |

## 11. 常用运维命令

```bash
# ── 本地开发 ──
pnpm run dev                          # API + 前端并行启动
pnpm run dev:api                      # 仅启动 Workers API (localhost:8788)
pnpm run dev:web                      # 仅启动 Astro 前端 (localhost:4322)
pnpm run build                        # 构建 API + 前端
pnpm run db:migrate                   # 手动执行本地 D1 迁移（dev 已自动执行）
pnpm run db:seed                      # 高级：交互式创建/更新管理员

# ── 部署 ──
pnpm run deploy:api                   # 部署 Workers API
pnpm run deploy:web                   # 构建并部署前端到 Pages
pnpm run db:migrate:prod              # 生产 D1 迁移

# ── D1 数据库 ──
wrangler d1 execute nami-blog --command "SELECT COUNT(*) FROM posts;" --config apps/api/wrangler.toml
wrangler d1 export nami-blog --output backup.sql  # 导出数据

# ── Workers / Pages ──
wrangler tail --config apps/api/wrangler.toml     # API 实时日志
wrangler pages deployment list                    # Pages 部署列表
wrangler pages deployment rollback                # Pages 回滚

# ── Cloudflare API ──
curl -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -d '{"purge_everything":true}'
```

## 12. 成本预估（MVP 阶段）

| 服务               | 免费额度                       | 预估月费  |
| ------------------ | ------------------------------ | --------- |
| Cloudflare Pages   | 无限请求，500 次构建/月        | $0        |
| Cloudflare Workers | 100K 请求/天                   | $0        |
| Cloudflare D1      | 5GB 存储，5M 读/天，100K 写/天 | $0        |
| Cloudflare DNS     | 无限                           | $0        |
| 域名               | —                              | ~$10/年   |
| **合计**           |                                | **$0/月** |

MVP 阶段完全零成本运行。随着流量增长，主要成本来自 D1 写入量，可通过 Cloudflare 付费计划线性扩展。
