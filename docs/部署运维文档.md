# 部署与运维文档

> 适用架构：Next.js + Hono + D1 + Workers KV，通过 OpenNext 部署到单个 Cloudflare Worker。

## 运行拓扑

```text
访客浏览器
  └─ Cloudflare Worker: nami-blog
       ├─ Next.js App Router
       ├─ /api/* → Hono API
       ├─ 静态资源
       ├─ D1 绑定：DB（真实数据源）
       └─ KV 绑定：CACHE（公开内容缓存）
```

生产地址：`https://nami-blog.codeelite.workers.dev`

Web 和 API 同源。当前架构没有 Cloudflare Pages、独立 API Worker、CORS 白名单和内容更新 Hook。

## 版本要求

| 组件 | 要求 |
| --- | --- |
| Node.js | 22+ |
| pnpm | 9+ |
| Next.js | 16.2.12 |
| OpenNext Cloudflare | 1.20.2 |
| Wrangler | 4.x |

精确版本以 `package.json` 和 `pnpm-lock.yaml` 为准。

## 配置来源

### 本地

API 和 Web 统一读取项目根目录 `.env`。模板为 `.env.example`。

```bash
pnpm install && cp .env.example .env
pnpm dev
```

本地公开地址默认为 `http://localhost:4322`。Next 开发环境通过 OpenNext 的 Cloudflare 上下文访问本地 D1。

### 生产公开配置

根目录 `wrangler.jsonc` 保存可以公开的配置：

- Worker 名称
- compatibility date/flags
- Assets 目录
- D1 数据库名称和 ID
- KV 绑定 `CACHE` 及其 Namespace ID
- `SITE_NAME`
- `NEXT_PUBLIC_SITE_URL`

`NEXT_PUBLIC_SITE_URL` 在生产构建时从 `wrangler.jsonc` 读取，避免开发者本机 `.env` 的 localhost 地址进入 canonical、RSS 或 Sitemap。

`pnpm build:worker` 会在构建期间临时隔离本地 `.env`，完成后自动恢复，并检查 Worker 产物中是否包含本地 JWT 密钥。生产密钥始终以 Cloudflare Secret 注入，不会写入构建产物。

### 生产 Secret

只在 Cloudflare Dashboard 保存：

- `ADMIN_INITIAL_PASSWORD`
- `JWT_SECRET`
- `JWT_REFRESH_SECRET`

密钥轮换会使现有会话失效。`JWT_SECRET` 与 `JWT_REFRESH_SECRET` 必须不同。

## 构建产物

```bash
pnpm build:worker
```

主要输出：

- `apps/web/.open-next/worker.js`
- `apps/web/.open-next/assets/`

这些目录是构建产物，已加入 `.gitignore`，不提交到仓库。

## 部署

完整部署：

```bash
pnpm deploy
```

它按顺序执行：

1. 构建 OpenNext Worker；
2. 对远程 D1 应用未执行的迁移；
3. 使用根目录 `wrangler.jsonc` 部署。

仅检查上传包而不发布：

```bash
pnpm build:worker
pnpm exec wrangler deploy --dry-run --config wrangler.jsonc
```

Cloudflare Git 集成推荐：

- Build command：`pnpm --filter @nami/web build:worker`
- Deploy command：`pnpm --filter @nami/web deploy:worker`

`deploy:worker` 已经包含远程 D1 迁移和 Wrangler 部署，Cloudflare 页面不需要再填写长命令。

## D1 迁移

本地：

```bash
pnpm db:migrate
```

生产：

```bash
pnpm db:migrate:prod
```

规则：

- 已发布迁移只追加，不回改
- 破坏性结构变更先写数据迁移与回滚方案
- 生产迁移前导出后台备份
- Git 部署日志必须保留迁移结果

## 动态内容一致性

以下数据以 D1 为准，成功写入后会清除 `nami:public:v1:` KV 缓存：

- 文章、分类、标签和友链
- 站点名称、副标题、SEO 描述、主题和评论开关

阅读统计和评论不进入 KV，始终直接读写 D1。

换域名、改代码或改 Worker 绑定才需要部署。

### KV 缓存策略

- 缓存：非搜索文章列表、公开文章详情、分类、标签、友链和公开设置。
- 不缓存：搜索、浏览量写入、评论、后台、认证、草稿、Secret、访客隐私和备份。
- 缓存有效时间：文章列表 2 分钟，其余公开数据 5 分钟；后台保存公开内容后会主动清理旧缓存。
- 降级：KV 未绑定或读写失败时直接读取 D1；缓存错误不改变 D1 写入结果。
- 排查：公开 API 的 `X-Nami-Cache` 会返回 `HIT`（来自 KV）、`MISS`（来自 D1）或 `BYPASS`（未使用 KV）。

KV 是最终一致存储，跨地区失效可能有短暂传播时间。缓存可以随时删除或重新创建，不属于备份和恢复范围。

## 健康检查

```text
GET /healthz
GET /api/v1/healthz
```

正常返回：

```json
{
  "status": "ok",
  "service": "nami-blog"
}
```

健康检查只表示 Worker 路由可执行。排查登录或内容错误时，还需查看 D1 绑定、migrations 和 Worker Logs。

## 发布验收

每次代码发布前：

```bash
pnpm check
pnpm test
pnpm build:worker
pnpm exec wrangler deploy --dry-run --config wrangler.jsonc
```

部署后至少检查：

- `/`
- `/blog`
- `/admin/login`
- `/api/v1/healthz`
- `/rss.xml`
- `/sitemap.xml`
- 登录、保存草稿、发布文章、前台立即可见

## 日志与隐私

Hono 的全局错误处理只向浏览器返回通用错误，实际异常写入 Worker Logs。

日志中禁止主动输出：

- 密码和 Secret
- Authorization Header
- Cookie 和刷新令牌
- 备份正文
- 评论者邮箱和 IP

共享日志前先脱敏。

## 备份与恢复

后台备份是允许列表格式，包含网站内容与公开配置，不包含凭据。推荐：

- 大改前导出一次
- 至少每月导出一次
- 备份文件离线保存两个副本
- 定期在非生产 D1 演练导入

导入采用“完整校验后替换”语义。版本、数量、唯一键或关联关系不合法时，不应先删除现有数据。

## 回滚

### Worker 代码

优先使用 Cloudflare 的版本与部署记录回滚到上一 Worker 版本，或在 Git 中 revert 后重新部署。

### D1 数据

Worker 回滚不会自动回滚 D1。数据库问题按以下顺序处理：

1. 停止继续写入；
2. 导出当前现场数据；
3. 评估修复迁移；
4. 必要时使用已验证的后台备份恢复；
5. 再发布兼容该结构的 Worker。

## Secret 轮换

1. 在 Cloudflare 修改 `JWT_SECRET` 和 `JWT_REFRESH_SECRET`；
2. 重新部署或等待变量生效；
3. 通知管理员重新登录；
4. 验证旧刷新令牌已失效。

修改 `ADMIN_INITIAL_PASSWORD` 不会重置已经创建的管理员。已有账号应在后台修改密码。

## 自定义域名变更

绑定域名后修改 `wrangler.jsonc`：

```json
"NEXT_PUBLIC_SITE_URL": "https://blog.example.com"
```

然后部署一次，并检查 RSS、Sitemap、robots 和页面 canonical。该值是构建期公开配置，Cloudflare Dashboard 中临时覆盖 Worker 变量并不能改写已经构建的客户端资源。

## 故障排查

### 500“服务暂时不可用”

检查：

1. D1 绑定名是否为 `DB`；
2. KV 绑定名是否为 `CACHE`；KV 异常时应回退 D1，而不是整站 500；
3. Database ID 是否属于当前账号；
4. 远程 migrations 是否成功；
5. JWT Secret 是否存在；
6. Worker Logs 的第一条异常。

### 登录循环返回登录页

检查浏览器 Network 中 `/api/v1/auth/login`、`/api/admin/dashboard` 和 `/api/v1/auth/refresh`。当前同源架构同时使用 HttpOnly Cookie 与标签页 Session Token，不依赖跨站 Cookie。

### 文章保存成功但前台不可见

检查 `status = published` 与 `is_public = 1`。再查看公开 API 的 `X-Nami-Cache`；后台成功保存会主动失效 KV，不要通过重新部署解决内容状态问题。

### RSS XML 无法解析

确认响应头为 `application/rss+xml; charset=utf-8`，根节点声明 `xmlns:content`，正文进入 CDATA，并运行 Web RSS 测试。

### 构建找不到 Wrangler 配置

`apps/web` 的 `build:worker` 已经通过安全构建脚本传入：

```text
--config ../../wrangler.jsonc
```

项目脚本已经包含该参数，不要在 `apps/web` 复制第二份 Wrangler 配置。
